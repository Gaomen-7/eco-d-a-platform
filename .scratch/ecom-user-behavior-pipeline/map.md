## Destination

写出一份 **spec-ready 的路线图**：它是解到 frontier 为空时**唯一**还站着的规划产物，内容 = 已跑通的 P0 环境、P1 实时闭环、P2 离线分层、P3 文档这四段的**定案**，直接供下一个 agent 会话施工，不再需要回溯 HLD/GDD/SRS 的推理现场。

**边界**：只到「知道怎么施工、判成没成」为止。实现本身、README 与 GIF 的制作、亿级回放的实际执行，都在目的地之外。
**不在目的地里的东西**：任何组件的版本锚点（C3 冻结）、路线选型、四个冻结端口之外的新端口、Makefile 八个冻结目标的名字——它们要改就走冻结项变更，不在这张图上解。

## Notes

- **域**：单机可复现的电商用户行为数据全链路（Kafka → Flink → Paimon / Doris → Superset）。本仓 `GLOSSARY.md` 是唯一术语表。
- **会话开始前必读**（按序）：`AGENTS.md` → 本文件 → `issues/map-dag.md` → 你选中的那张票。
- **每解一张票要调的技能**：`grilling` + `domain-modeling`（HITL）；`research`（AFK，可并行）；`prototype`（HITL）。
- **本 effort 的常驻纪律**（从上游继承，逐条都有出处）：
  1. **参数性质边界**：每个数字标 `官方给出` 或 `设计值`，**不得把设计值当官方保证**（HLD §0.3）。
  2. **行为可证**：每条约束附检查方式与判定条件；「配置可见」「UI 里能看到」不是判据（HLD §0.4、gdd §0）。
  3. **实机验证**：凡涉及「按某格式写配置」「镜像里有什么」「数据落在哪」「指标是否可信」，**先实机验证再写进文档**——P0 已在四处被官方说法打脸（HLD §8-R7）。
  4. **能起来 ≠ 能重起来**：凡把状态持久化进卷的组件，验收判据必须包含一次「不删卷的重启周期」（HLD §7.3 方法论收获）。
  5. **代理测试必须用真实同类对象复验**（HLD §8-R4 教训：代理的性质不是被代理对象的性质）。
  6. **git**：agent 只做本地提交，**不推送**；推送由用户执行。
- **本地改动先获批**：任何本地文件/配置改动（含安装类操作）先征得同意、先备份、说明回滚，再执行。
- **票的物理形态**：`.scratch/ecom-user-behavior-pipeline/issues/NN-<slug>.md`；`Status:` ∈ `open` / `claimed` / `resolved`；`Blocked by: NN, NN`；`Type:` ∈ `research` / `prototype` / `grilling` / `task`。
- **一次会话只解一张票**（research 票例外，可批量）；解前先把 `Status: claimed` 写盘。

3. **F3 · 生成器 live 模式的确定性**（挂 [04]）：`REQ-F-GEN-06`（同种子同哈希）在 live 模式下要同时满足「pin 到补丁号的 Faker」「同种子」「按速率写」——速率是墙上时钟量，三者是否能同真，现在说不清。
4. **F4 · 迟到计数表落在哪**（挂 [03] / [01]）：`gdd D10` 说「超期→迟到计数表」，但没定它是 Doris 内表（受 unique key 与唯一写入者约束）、Paimon `late_*` 表，还是独立 topic。
5. **F5 · `client` 何时不该存在**（挂 [06]）：`client` 只服务 Stream Load 两跳与 Doris 断言；若换执行面（Podman 备选），它可能从必需降为可选 profile。先看 [06] 的边界怎么划。
6. **F6 · Superset 交付形态是否 = zip**（挂 [04]）：`gdd §1.7` 写 `superset import-dashboards -p <.zip>`，但 `REQ-F-BI-01..04` 从未说交付物是 zip；若交付物是「打开浏览器就能看」，zip 是手段不是判据。
7. **F7 · 含数据卷 vs 干净机器，哪条是「一条命令」**（挂 [06]）：`REQ-NF-CAP-03` 是「预拉镜像前提下 ≤15 分钟」，`REQ-F-ORCH-01` 是「干净机器一条命令」；两条判据的操作化（含不含 `down` 后的卷）不一致。
8. **F8 · `verify` 的边界**（挂 [09]）：HLD §3.3-6 把 `lint`/`typecheck` 另设目标、不混入 `verify`，但 `REQ-F-VERIFY-01` 只说五项烟测；`verify` 是否还要覆盖 `REQ-F-VERIFY-02`（幂等）、`REQ-F-VERIFY-05`（lag）未定。
9. **F9 · 降级阶梯的触发条件**（挂 [04]）：HLD §8-R6 的「Superset 减服务 A/B/C」与 gdd §1.11 的 G4（Kafka 原生镜像）都没写「什么信号出现才降级」，以及降级后谁回填实测。
10. **F10 · 2 GB 上限的实际保留窗 ~6h 够不够**（挂 [03]）：`REQ-F-MQ-03` 是冻结项；先由 [03] 定「REQ 冲突谁让路」的口径，再决定是提冻结项变更、还是把 P1 的可证窗控制在 6h 内。
11. **F11 · DIM 拉链正确性的判据**（挂 [08]）：`gdd D6.1` 定了字段与「无重叠无空洞」，但断言形态（逐 `item_id` 逐 `event_time` 全对比？抽样？何时修）未定。
12. **F12 · 离线不变量断言的对账口径**（挂 [08]）：`gdd §1.4` 写 `ODS 行数 = DWD 行数 + 拒绝表行数 + 迟到标记差异`，但「迟到标记差异」不是可加的项，精确等式待写。
13. **F13 · Paimon compaction 在 `file://` 下的成本**（挂 [01]）：`REQ-F-LAKE-08` 要求定期 compaction；`gdd` 说「保持官方默认」。官方默认在本地文件系统上的实际开销未测得，与磁盘 20GB 预算（R5）可能相撞。

## 为什么建议第一个目标是 [04]

四条理由，按权重排：

1. **它决定目的地长什么样**。本图的目的地是「spec-ready 路线图」，而路线图的第一段就是 P1。不先钉死「P1 怎样算成立」，后面 02/09/05/10 全都在猜一个不存在的边界。
2. **它会把迷雾大批清掉**。F3、F6、F9 三条迷雾直接挂在它下面；解完它，3/13 的迷雾要么毕业成票，要么消失——这是地图上前沿推进性价比最高的单步。
3. **它是阻塞最多下游的那一张**。[03]、[09]、[05]、[07]、[02] 以及迷雾 F1、F2 都排在它后面；先解它，后续会话不会各按各的定义走。
4. **它是 HITL（grilling）**，而它要问的东西**只有你能回答**——「我的作品/面试素材里，P1 要证到什么程度」。任何 agent 代答都会变成又一份「按推荐」的假设，而那正是本仓历史上最大坑的来源（HLD §0.3）。

**反方意见（也写在这里，供你否掉我）**：如果你现在更想先修文档的互斥与信任缺口，而不是定 P1 的成功判据，那么正确的第一个目标是 **[03] REQ 冲突裁决口径与 D1–D15 收口顺序**。代价是：它把刚清掉的一批迷雾（F4/F10）又塞回讨论，且[04] 仍会拦住 [05]/[09]——**地图会变长，前沿推进变慢**。这一取舍我没有替你决定。
