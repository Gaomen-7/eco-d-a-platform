# impl-07a: 脏率基线同步脚本 —— 解析失败报真因 + 只解析一次

Type: task
Status: resolved
Blocked by: None（可立即开工）

**What to build:** 脏率基线同步脚本在读基线失败时，要说出**真正的原因**——是解释器不在、
是解释器在但不可用、是文件内容坏了、还是文件里缺字段——而不是一律报「基线文件不可解析
（缺 X 字段？）」。今天后者会把排查方向引向「基线文件坏了」，而真因常常在执行面上。

同时把「同一个基线文件解析两次」收敛成一次，并处置那个**只打印不参与判断**的多余解析。

## 背景：为什么「文件坏了」是个误诊

这个脚本读基线文件时把标准错误流丢掉了，于是**任何**失败都只剩一句「不可解析」。
但失败至少有四类，而其中一类**文件完全完好**：

| 故障 | 文件状态 | 今天的报错 | 真实原因 |
| --- | --- | --- | --- |
| 解释器不在 PATH 上 | 完好 | 基线文件不可解析 | 解释器缺席 |
| 解释器在 PATH 上但**不可用** | 完好 | 基线文件不可解析 | 解释器是空壳/损坏 |
| 文件是坏 JSON | 坏 | 基线文件不可解析 | 文件损坏 |
| 文件缺字段 | 缺字段 | 基线文件不可解析 | 字段缺失 |

第二行是最恶劣的一类：文件没问题，脚本却指控文件。**有些宿主上 `python3` 指向应用商店
安装器的空壳跳转程序**——存在性探测会通过，执行却静默失败且不吐任何错误信息。
⇒ 存在性探测抓不住它，只有**真的执行一次**才能分辨。

## ★ 与 impl-05 原文的出入（照原文做会做错）

impl-05 §5 给的修法建议是「建议先 `command -v` 探测」。**这条已被实测证伪**——
空壳解释器存在性探测会放行。正确修法是**执行一次最小语句做自检**。
本票取代该建议，母票 [impl-07](impl-07-panel-baseline-parse-and-interpreter.md) 留档。

## 两条附带的处置

**（甲）同一个文件解析两次** —— 脚本为了取两个键，把同一个基线文件交给解释器解析了两次。
两次解析之间文件可能被改写，理论上可能两次读到不同内容。收敛成一次即可消除该面。

**（乙）多余的解析** —— 第二次解析取的那个「输入事件数」键，**只被打印、从没参与任何判断
或写入**（面板那一行写入用的是**当前**的输入总数，不是基线里的）。它多一个失败点
（多一个误诊机会）却零收益。⇒ 处置：要么删掉这个读取，要么明确它是「仅供日志参考」并
从「解析失败即致命」里摘出来。**处置方向由实现者定，但必须让票面与行为一致**——
不能留一个「解析它、只为了打印、失败还致命」的三不像。

## Acceptance criteria

- [x] 读基线失败时，报错**指明真因**并可据以行动：至少能区分「解释器不可用」与
      「基线文件读不出目标值」两大类（后者再区分「JSON 损坏」与「缺字段」更好）
- [x] **解释器不可用这一类能被抓到**——判据是「解释器真的能执行一条最小语句」，
      不是「解释器在 PATH 上」（空壳解释器必须被这一条抓住）
- [x] **反例凭证**：构造一个「存在但不可执行」的假解释器（如指向一个退非 0 且不吐 stderr
      的脚本），跑同步脚本 ⇒ 必须报「解释器不可用」这一类，**不得**报「基线文件不可解析」
- [x] **正例凭证**：基线文件完好 ⇒ 解析成功、后续步骤与施工前行为一致（见母票收口门）
- [x] 基线文件**只解析一次**；若仍解析两次，须给出为何不能收敛的实测理由
- [x] 那个「只打印不参与判断」的输入事件数读取已处置：要么移除，要么明确为仅日志参考且
      **不再导致致命失败**——两种都可以，但行为与票面须一致
      ⇒ **选定「仅日志参考」**：`dlq_offset` 是唯一必需字段；`input_events` 缺失时打印
      `<缺失·仅日志参考>` 并继续，正常路径的打印逐字不变（见 Answer §3）
- [x] 报错信息里带**可操作的下一步**（该做什么），不是只说哪里错了
- [x] 新增守卫测试钉住「不再有裸 `2>/dev/null` 吞掉解析错误」这一形态；
      全量 pytest 仍全绿
- [x] 脚本语法自检通过；**正常路径的输出与施工前逐字一致**（除错误分支外零变化）

（不是存在性探测）；基线只解析一次；`input_events` 降级为「仅日志参考」、缺失不再致命。
正常路径与施工前**逐字一致**（stdout/stderr/退出码三面 diff 全 PASS）。**未改口径、未动 Δ 计算、

### §1 改动（只碰报错分支与解析次数）

| 位置 | 施工前 | 施工后 |
| --- | --- | --- |
| `superset-dirty-rate-sync.sh` ⓪（新增） | 无解释器自检 | 执行 `-c "print('impl07a-probe-ok')"`，**只比对 stdout 与退出码**，stderr 单独收集仅供诊断；成功时零输出 |
| ① 解析 | 两个解释器进程各取一个键，`2>/dev/null` 吞掉一切证据 | **一次**解析产出机读标签，失败按标签分流并**保留解释器 stderr** |
| ① 报错 | 一律「基线文件不可解析（缺 X 字段？）」 | 七类真因：缺席 / 不可用 / 读不出 / 坏 JSON / 顶层非对象 / 缺字段 / 类型或符号不对 |
| ① `input_events` | 缺失即致命 | 缺失打印 `<缺失·仅日志参考>`，**不致命**（它从不参与判断或写入） |
| ② offset 校验 | `[ -n ... ] && [ ... -ge 0 ] 2>/dev/null` | `require_offset` 纯十进制校验（消除最后一处 stderr 静默） |

**为什么不是 `command -v`**（票面 ★ 出入 1）：实测空壳解释器存在性探测**通过**、执行静默退 49、
stderr 零字节——只有真的执行才能分辨。取证件 `01-fault-injection.out.txt` 的 `[2b]` 段逐字记录了
这两个相反结论（存在性：通过；真执行：rc=49 / stderr 0 字节）。

### §3 「（乙）多余的解析」的处置：选定「仅日志参考」

票面允许两种处置，**本票选后者**并让行为与票面一致：

- `dlq_offset` 是**唯一必需字段**（它参与 Δ 计算与面板写入）；
- `input_events` 只用于那行日志——面板 `total_events` 行写的是**当前**输入总数（`cur_input`），
  与基线里的值无关。故它缺失打印 `<缺失·仅日志参考>` 并继续，**不再致命**；
- 同一把解析把它与 `dlq_offset` 一次取出 ⇒ 解析次数由 2 降为 1（旧形态两次解析之间文件可能被
  `make verify` 前推；impl-07c 的原子替换正是在这一面补刀）。

### §5 新增守卫测试（`tests/test_dirty_rate_sync.py`，13 条）

钉住票面点名的形态，不自证实现：

- **不再有裸 `2>/dev/null`**：全脚本零出现（不是只钉解析段——那挡不住下一个人把它搬回别的分支）；
- **自检判据是「执行 + 核对 stdout」**：不得出现 `command -v`，且**不得把 stderr 折进哨兵比对**

- 四类真因互不冒充 + 每条都带下一步动作；
- **只解析一次**（用计数包装解释器数 argv：恰好 2 次调用 = 自检 1 + 解析 1，其中带基线路径的恰好 1 次）；
- 正常路径输出逐行比对（期望值手写，不从脚本推）；
- `input_events` 缺失不致命；`dlq_offset` 类型/符号不对各一条。
