## ★ 三处与 impl-05 原文的出入（复核后修正，照 impl-05 原文做会做错）

**出入 1：① 里「建议先 `command -v` 探测」这条修法已被实测证伪。**
`command -v` 只检查解释器**在不在 PATH 上**，但一个**存在却不可用**的解释器照样放行。
实测反例：某些宿主上 `python3` 指向应用商店安装器的空壳跳转程序——`command -v python3` **通过**，
而执行任何代码都**静默退 49 且 stderr 一个字都不吐**。此时一份**完好**的基线文件会被报成
「基线文件不可解析（缺 dlq_offset 字段？）」，与真因（解释器不可用）完全无关。
⇒ 正确修法是**真的跑一次解释器自检**（能否执行一条最小语句），不是存在性探测。
**任何接手者不要照 impl-05 原文的 `command -v` 建议做。**

**出入 2：② 的归并范围被高估。**
两处内联 `python -c` 的**输入源与语义都不同**：基线同步脚本从**文件**读、取两个数值键；
置备脚本从 **stdin** 读、取一个对象里的标识符。⇒「读文件取多键」这个辅助只覆盖前者，
后者**共用不上**，不归并。本票据此拆成 07a（文件面）与 07b（stdin 面）两张。

**出入 3：② 顺带暴露一个票面未记的缺陷。**
基线同步脚本第二次解析取的那个「输入事件数」键，**只被打印、从没参与任何判断或写入**——
面板那一行写入用的是**当前**的输入总数，不是基线里的。⇒ 这是一次多余的解析，多一个
失败点（多一个误诊机会）却零收益。07a 一并处置。

### §1 ★ 留档一：impl-05 原文「先 `command -v` 探测」的建议已被证伪（勿照做）

母票 §「出入 1」写下的这条，本票用**可复跑的反证**落地，而不是只留一句断言：

门 A 的 `[2b]` 段（[`.out.txt`](../evidence/impl-07/01-baseline-chain-fault-injection.out.txt) 内）
构造一个「存在但不可执行」的假解释器（`#!/bin/sh` + `exit 49`，零输出零 stderr），然后：

```
✓ 存在性探测：**通过**（放行了一个不可用的解释器 —— 所以它不能当判据）
✓ 真跑一次：rc=49、stdout=0 字节、stderr=0 字节（静默失败 ⇒ 只有真的执行才分辨得出）
```

于是同一次运行里：

| 判据 | 空壳解释器 | 判决 |
| --- | --- | --- |
| `command -v`（存在性探测） | **通过** | 会放行 ⇒ **不可用作判据** |
| 真执行一条最小语句 + 核对 stdout | rc=49 / 输出不符 | **抓得住** |

★ 这台机器上还有一份**现成的、非人造的**同类样本：宿主 `python3` 指向
`…\WindowsApps\python3.exe`（应用商店安装器的空壳跳转程序）。它的**退出码取决于调用方**：

| 调用方 | 实测退出码 | stdout | stderr |
| --- | --- | --- | --- |
| Git-Bash（本仓脚本与测试的默认执行面） | **49** | 0 字节 | 0 字节 |
| 原生 Windows（PowerShell `$LASTEXITCODE`） | **9009** | 0 字节 | 0 字节 |

两者都**不是 0**、都**不吐 stderr**，故「存在但不可用」这个结论对两种调用面都成立；
但**具体数值随调用面不同**，票面不要再写死成「退 49」——那是 `gate A [2b]` 用的**人造**
桩脚本的值（`#!/bin/sh` + `exit 49`），与这个天然样本是两回事。
（★ code-review 的 Spec 轴指出过这一处措辞过强，已按实测拆开：人造桩 vs 天然样本、两个调用面。）

这也解释了为什么本仓脚本必须真的执行一次而不是查 PATH
（`Makefile` 的 `PYBIN ?= python3` 与 WSL 内的 `/usr/bin/python3` 是两回事）。

⇒ **任何接手者不要照 impl-05 §5 原文的建议做。** 正确修法是「真的跑一次解释器自检」——
07a 已按此实现；门 A 每次复跑都会把这条反证重新打一遍。
