# impl-07: 面板基线解析口径与解释器可用性 — 母票（索引 + 收口门）

Type: task
Status: ready-for-agent
Blocked by: impl-07a, impl-07b, impl-07c

**What to build:** 让脏率基线链上的任何一步失败都报**真因**（解释器缺席 / 解释器是空壳存根 /
JSON 损坏 / 字段缺失 / 接口结构变了），而不是一律报「基线文件不可解析」。今天这个误诊会把
运维引向「基线文件坏了」的方向，而真实原因可能在执行面上。

本票是**索引 + 收口门**，自身不施工——三张副票各改一个面。

## ★ 三处与 impl-05 原文的出入（复核后修正，照 impl-05 原文做会做错）

**出入 1：① 里「建议先 `command -v` 探测」这条修法已被实测证伪。**
`command -v` 只检查解释器**在不在 PATH 上**，但一个**存在却不可用**的解释器照样放行。
实测反例：某些宿主上 `python3` 指向应用商店安装器的空壳跳转程序——`command -v python3` **通过**，
而执行任何代码都**静默退 49 且 stderr 一个字都不吐**。此时一份**完好**的基线文件会被报成
「基线文件不可解析（缺 dlq_offset 字段？）」，与真因（解释器不可用）完全无关。
⇒ 正确修法是**真的跑一次解释器自检**（能否执行一条最小语句），不是存在性探测。
**任何接手者不要照 impl-05 原文的 `command -v` 建议做。**

**出入 2：② 的归并范围被高估。**
两处内联 `python -c` 的**输入源与语义都不同**：基线同步脚本从**文件**读、取两个数值键；
置备脚本从 **stdin** 读、取一个对象里的标识符。⇒「读文件取多键」这个辅助只覆盖前者，
后者**共用不上**，不归并。本票据此拆成 07a（文件面）与 07b（stdin 面）两张。

**出入 3：② 顺带暴露一个票面未记的缺陷。**
基线同步脚本第二次解析取的那个「输入事件数」键，**只被打印、从没参与任何判断或写入**——
面板那一行写入用的是**当前**的输入总数，不是基线里的。⇒ 这是一次多余的解析，多一个
失败点（多一个误诊机会）却零收益。07a 一并处置。

## ★ ③ 的留档判定（不开票的理由）

impl-05 登记的「`JID` 硬编码为取证当时的旧作业」经复核**判定不施工**：

- 全仓检索确认：除 impl-05 票面那一行自述外，**没有任何地方引用**这两个取证辅助脚本。
  它们是**取证存档件**，已入库，存档语义自洽。
- Flink 每次提交作业生成新 JobID ⇒ 硬编码**本来就是**一次性快照的固有属性，
  「硬编码」不是缺陷，是取证件该有的形态。
- 改成「运行时查最新作业」等于给一个零引用的取证件**加功能**，偏离其定位，且引入新的
  失败面（要判断哪个作业是「最新」）。

⇒ 结论：③ **不单开施工票**。原始文件一字不动。本条作为母票留档判定记录在此，
以免下一个接手者再翻一遍同样的账。

## Notes

- **本票与 impl-05/impl-06h 的关系**：impl-06h 已把**基线口径**（谁写基线）按实现改准
  （`make verify` 棘轮，裁决 A）。本票不动口径，只动**失败时的报错形态**与**落盘原子性**。

  变化一律视为回归。
- 三张副票之间**互不阻塞**（各改各的面），可并行开工；本票是它们的收口门。
- 脚本改动只碰**报错分支与解析次数**，不改任何计算逻辑、不改面板写入形态。
