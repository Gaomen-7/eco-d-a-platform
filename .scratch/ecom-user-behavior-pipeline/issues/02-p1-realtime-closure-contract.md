## Question

目的地是「spec-ready 路线图」，而路线图第一段是 P1。`SRS §7` 把 P1 定义为一长串需求的集合（`REQ-F-GEN-*`、`REQ-F-MQ-*`、`REQ-F-RT-01..08`、`REQ-F-OLAP-01..03`、`REQ-F-BI-01..04`、`REQ-F-VERIFY-01/02`），**没有一条说「P1 做到这里就算成立」**。于是：

- 迟到修正（`REQ-F-RT-04`）、DLQ 分类（`REQ-F-RT-07`）、`verify-fault`（`REQ-F-VERIFY-03`，SHOULD）——是 P1 的一部分，还是「P1 尾巴」？
- 脏率面板（`REQ-F-BI-04`，SHOULD）与「暂定/落定视觉区分」（gdd §1.6，`【已确认 Q13】`）——哪一个是硬条件？
- 冷启动 ≤15 min（`REQ-NF-CAP-03`）、≤8 GB（`REQ-NF-CAP-01`）——是 P1 的**门槛**还是之后的**记账**？
- `gdd §1.3` 新增的四条「行为可证」判据（`revision > 0` 出现、脏率不上升、漏斗单调、UV 与离线逐窗口相等）——几条是 P1 必须证明的？

**要产出的一张圈表：**

| 圈 | 含义 | 读法 |
| --- | --- | --- |
| **PI-1 最小闭环** | 不成立则 P1 不成立 | 每条给一个**可执行断言**（退出码 / 标量 / 字段） |
| **PI-2 加固** | 成立则更好，不阻塞进入 P2 | 写明延到哪一段 |
| **PI-3 标注** | 只要求在文档里标注风险/口径，不要求实现 | 例如 Experimental 的 early-fire |

并回答：**「P1 成立」的判定动作是什么**——一次 `make verify` + 一次人工看板观察（GIF）？还是三条独立的机器断言？谁签字。

## 约束

- 不碰冻结项（八个 Makefile 目标名、四个端口、`ecom_ads` / `ecom_lake` 库名）。

## Answer

**Resolved 2026-10-20（本会话，map 落子时一并裁决；用户可推翻）。** 详细推理见 [map.md](../map.md) 的「为什么建议第一个目标是它」与 Decisions so far 的 D4。

**裁决：本票不再问「P1 做什么」，只问「P1 怎样算成立」。**

1. **目的地已把它收窄**：`map.md` 的 Destination 是「一份 spec-ready 路线图」，不是「一个能跑的 P1」。实现属于路线图的下游（施工），不属于路线图本身（决策）。
2. **仓库里没有任何文档定义「P1 完成」这个状态**：SRS §7 给需求集合，FSR §9 给里程碑名 + 一句判据，gdd 给判据的**零件**。零件 ≠ 判定动作。
3. **它卡住最多下游**（[01]/[03]/[04]/[05] + 迷雾 F1/F2/F3/F6/F9），且是 HITL——答案只有你能给（「我的作品要证到什么程度」），agent 代答就是又一次「按推荐」。

**连带裁决**（同时改写了这张图的构成，逐条见 map.md 的 D4）：目的地收窄；**冻结面不进图**（C3 锚点、八个目标名、四个端口、两个库名）；**设计面就地落子**（冷启动预算、回滚三件套、DAG 本体）。

**未吸收的口子（保留，不要当成已决）**：P1 圈表的**具体切法**仍要你裁决——那正是本票留白的原因；`REQ-F-LAKE-08` 的验收判据归属并入 [01]（唯一真相源）一并收口。

**下游影响**：迷雾 F3（live 确定性）、F6（Superset delivery）、F9（降级触发）仍挂在 [02] 名下，等圈表定下来再决定毕业与否。
