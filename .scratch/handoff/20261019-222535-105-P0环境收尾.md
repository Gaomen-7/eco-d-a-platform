## 5. ★★ 本会话踩过的坑（**接手前必读，避免重踩**）

这批坑的性质都一样：**「官方文档说应该怎样」≠「实机实际怎样」**。四次不一致，每次都真的失败过。

| # | 坑 | 症状 | 修法 |
| --- | --- | --- | --- |
| 1 | **Flink 2.2 的配置是 `config.yaml`（YAML）**，不是 `flink-conf.yaml`，**也不吃 `FLINK_PROPERTIES`** 那套点号键 | 按调研笔记写法配置**完全不生效** | 用 `docker/flink/conf/config.yaml`（只写差异项） |
| 2 | **不能把空目录 bind 进 `/opt/flink/conf`** —— 会遮住镜像自带的 `config.yaml` | `The Flink config file '/opt/flink/conf/config.yaml' does not exist`，flink-jm 变 unhealthy | 改为**挂单文件**：`./docker/flink/conf/config.yaml:/opt/flink/conf/config.yaml:ro` |
| 3 | **`apache/superset:6.1.0` 镜像不含任何 DB 驱动**（`psycopg2`/`psycopg`/`mysqlclient`/`pymysql` 全 MISSING） | 用 Postgres 元数据库时 worker 启动即 `ModuleNotFoundError: No module named 'psycopg2'` | 元数据库改 **SQLite**（镜像自带 sqlite3 3.40.1）；`ecom_ads` 所需 MySQL 驱动经**官方机制** `/app/docker/requirements-local.txt`（`docker-bootstrap.sh:35`）装 **PyMySQL** |
| 4 | **Kafka 4.3.1 的 `kafka-topics.sh` 不再支持 `--alter` 改配置** | 建 topic 时施加 retention 直接失败（报错指向 `kafka-configs` 工具） | 改用 **`kafka-configs.sh --alter --entity-type topics`** |
| 5 | ★★ **named volume 挂上去 ≠ 数据落在里面** ★★ | 官方 `apache/kafka:4.3.1` 默认 `log.dirs=/tmp/kraft-combined-logs`（`server.properties:73`）——**`/tmp` 是容器内路径** ⇒ `down/up` 后数据**全丢**（实测 offsets 1→0，卷内容为空）。**这使 `REQ-F-ORCH-05` 真实失效** | 显式 **`KAFKA_LOG_DIRS=/var/lib/kafka/data`**。复验：`restart` 3→3、**`down`+`up` 3→3** |
| 6 | **Kafka healthcheck 探针太重 ⇒ 假 unhealthy** | 原探针用 `kafka-broker-api-versions.sh`，**每次起一个 JVM，实测 37.7 秒**，而 `timeout` 只有 10s ⇒ **永远超时**（实测 `FailingStreak=22`），容器长期显示 `unhealthy`，**但功能完全正常**（topic/offsets/生产消费都可用）。这还会**阻断依赖它的服务**（`kafka-init`、`client` 用 `condition: service_healthy`） | 改用**轻量 TCP 探针**（实测 4.6s、不依赖 JVM）：`test: ["CMD-SHELL", "timeout 3 bash -c 'exec 3<>/dev/tcp/localhost/9092' || exit 1"]`。改后实测 **`healthy` / `failing=0`** |

> **第 6 条的教训**：**探针失败 ≠ 服务失败**。看到 `unhealthy` 先做**功能探测**（能否 list topic / 读写数据）再判断，别急着当成故障去修服务。这是本会话第二次遇到「指标与事实不符」（第一次是 §5-7 的代理测试）。

**另外三处 「agent 自己写错」**（都已修，供警惕）：
- `Makefile` 里内嵌 heredoc → make 把 Python 当 makefile 语法 ⇒ `missing separator`。**逻辑移入 `scripts/config_check.py`**
- `verify` 里 `$fail` 少写一个 `$`（被 make 展开成空）⇒ 退出码显示错
- **`up` 的落点判断一度错了**：我曾用「等价 Windows 监听」做**代理测试**，得出「WSL 连 `127.0.0.1` 一律不可达」；后用**真实 Docker 发布端口**复测，**结论相反**（WSL 内 `curl 127.0.0.1:8081` = 200、`:8088` = 302、`:9092` TCP OK）。**代理测试必须用真实同类对象复验**。HLD §4.7/§8-R4 已改正，「必须用 `python.exe` 探测」的约束已撤销。

**方法论（已写进 HLD §8-R7 的教训栏）**：凡涉及
①「按某个格式写配置」②「镜像里有什么」③「数据落在哪」④「CLI 版本行为」
的结论，**必须实机验证一次**才能进施工路径。
